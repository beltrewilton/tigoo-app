# Sign the DGII application XML

`TigooServer.Sign` supports the `Postulacion` document generated by DGII's portal.
It uses the existing enveloped RSA-SHA256 XMLDSig implementation with the supplied
PKCS#12 certificate, and verifies the generated signature before returning it.
This does not verify the applicant's registration or representative authorization;
use the certificate of the representative named in the application.

From `server`, with the updated signer already compiled:

```bash
bash sh/sign_fe_postulacion.sh ans ../fe/202610253240465.xml
```

The script loads `.env`, reads the single `.p12` in `p12_companies/ans/` and its
password from `credentials.txt`, and creates:

```text
fe/202610253240465.signed.xml
```

For production, select its environment and tenant explicitly:

```bash
MIX_ENV=prod ENV_FILE=.env-prod bash sh/sign_fe_postulacion.sh evofitdb ../fe/202610253240465.xml
```

An optional third argument selects another output path. XML paths are relative
to `server`, or absolute. The script refuses to overwrite existing output files.
It uses `mix run --no-compile --no-start`: it does not compile the application,
start Phoenix, connect to the database, or call any HTTP endpoint. It only creates
the signed output and temporary signing files, which the signer cleans up.

In DGII's portal, choose the resulting `.signed.xml` using **Elegir archivo**,
then **ENVIAR ARCHIVO**. Do not format or modify the file after signing it.
The script does not upload anything automatically or alter the source XML.

## POS wizard

Open **Certificación DGII** in the POS sidebar (`/pos/dgii-certification`).
Access requires the existing `company.settings` permission. Step 1 accepts one
Postulacion XML up to 5 MB, signs it with the authenticated tenant's single
`.p12` and `credentials.txt` under `fe_receivers_directory/<tenant>/`, and offers
the signed bytes as a download. It reuses `Fe.Credentials` and `Sign.sign/3`,
without invoking the shell script or accepting a tenant from the upload form.

The signed XML download is available only for the current page session; no
signed document or certification progress is persisted. Signing identity files
uploaded in step 0 are persisted in the tenant directory. Upload the downloaded file to DGII manually.
Step 2 submits existing signed certification cases. Steps 3–15 are placeholders pending implementation.

### Step 0: signing identity

Upload the tenant's `.p12` and `credentials.txt` in **Certificado digital**.
The server creates `fe_receivers_directory/<authenticated tenant>/` as needed.
The certificate is limited to 5 MB and credentials to 64 KB. The credentials
filename must be `credentials.txt`, with exactly one `Password:` or `Password=`
field. The existing signer checks the certificate/password pair using a local
sample document before saving; nothing is submitted to DGII.

Uploaded identity files are stored with mode 0600. A new pair replaces the
existing pair; the existing certificate filename is retained so the signer
still finds exactly one `.p12`. A directory with multiple `.p12` files must be
resolved before uploading. Saving continues to Postulación.

### VersionSoftware rejected by DGII

DGII declares `VersionSoftware` as `xs:double`. A semantic version such as
`1.0.0` is invalid; use the corresponding numeric software version (for example
`1.0`) in the original unsigned application XML, then upload and sign it again.
Step 1 rejects invalid values before signing and shows this correction. The
signer preserves the source value; never edit the already signed download.

## Step 2: submit signed certification cases

**Casos de prueba** lists existing generated ECF batches whose authorized issuer
RNC matches the authenticated tenant's single active company. Upload an XLSX
to generate a new signed batch, or select a previously generated batch. Configure the batch root
with `FE_CERTIFICATION_BATCH_DIRECTORY` (default `fe/data-test/generated`).

The UI calls the same `Client.new/1` and `Submission.run/3` flow as
`sh/submit_fe_certification.sh`, with `environment: "certecf"` fixed on the server,
`expected_document_type: "ECF"`, 20 poll attempts, and a 1-second poll interval.
It uses the current tenant's step-0 credentials and the existing batch journal
`submission-certecf.json`; accepted cases are skipped and pending Track IDs
are queried without reposting. Submission runs asynchronously and updates the
case table as results arrive. Reloading the page reads the saved journal.

The existing sender validates the batch before HTTP, sends in dependency order,
routes low-value consumption cases through RFCE, and stops on rejection or an
uncertain reception. Their full ECF XMLs still require manual portal upload.
The UI displays saved DGII responses and errors so those cases can be reviewed.
No environment selector or journal reset is exposed. Opening the page never
posts documents; the user starts submission with the CerteCF send button.

### Generate cases from an uploaded XLSX

Step 2 starts with **Generar casos desde XLSX**. Select one `.xlsx` file up to
20 MB; upload begins immediately. **Generar y firmar casos** runs the same
`Generation.generate/1` API used by `sh/generate_fe_certification.sh`, using the
authenticated tenant's active-company RNC and step-0 signing identity. The first
worksheet must be `ECF`; workbook and source-preservation validation stay in the
existing generator. Generation runs asynchronously and reports validated cases.

Each run publishes a unique batch under the configured certification directory
without overwriting earlier batches. Successful source workbooks are retained
under `.sources/<tenant>/` with mode 0600 for manifest provenance. Failed
uploads are removed. The generator publishes the batch only after all checks
pass. Newly generated `dgii_data_tests` manifests and legacy manifests without
a purpose are both supported by the submission UI.

On success, the new batch is automatically selected in the submission section.
Generation makes no DGII requests; **Enviar / continuar casos en CerteCF** is
a separate action. Arithmetic observations are reported without changing the
workbook's supplied values, matching the CLI's default behavior.

The generation rules and currency interpretation are documented in
[FE_GENERATION_GUIDE.md](FE_GENERATION_GUIDE.md), with printed-page references
to the local DGII format guide. Missing currency means local DOP in the
manifest; it does not produce a `TipoMoneda=DOP` foreign-currency XML tag.

### Download low-value full ECFs

Step 2 lists individual XML downloads under **Descargar documentos de consumo menores a
RD$250,000** for each eligible type-32 case in the selected batch. Each case
has separate **Descargar resumen RFCE** and **Descargar ECF íntegro** links,
available immediately after successful generation. Each case shows the saved
RFCE status.
Downloads require an authenticated user with company settings access, a batch
matching the tenant's RNC, and a file checksum matching the manifest. The
original signed bytes and filenames are preserved.

Reference: `fe/Descripcion Tecnica Servicios DGII.pdf`, p. 15, section
“Recepción de resumen factura de consumo electrónica (RFCE)”. This distinguishes
the signed summary received by the RFCE service from the full extended ECF
that the taxpayer must retain. The exact combined term “Resumen de Factura de
Consumo Íntegro” was not found in the repository guides. The UI therefore
labels the two artifact types separately. RFCE downloads use the manifest's
`rfce_file` and `rfce_sha256`; full ECF downloads use `ecf_file` and `ecf_sha256`.
